Web Application Firewall

The WAF (Coraza with the OWASP Core Rule Set) inspects every request for SQL injection, cross-site scripting, path traversal and similar attacks before it reaches your service. One global policy covers every proxy rule that follows it; single rules can use a profile or their own settings. Nothing changes until you turn it on.

Each matching rule adds points (critical 5, error 4, warning 3, notice 2). A request is blocked when the total reaches this number. Lower = stricter.
Only this much of a request body is inspected.

Graduated response (log, challenge, block)

Instead of a hard 403 for every borderline request, add a middle band: a visitor whose score is between the challenge threshold and the block threshold gets a CAPTCHA page once, and passes for the validity time after solving it. Scores at or above the block threshold (the anomaly score threshold above) are still blocked, and a solved challenge never opens that band. Challenged requests do not count towards the automatic ban.
Must be lower than the anomaly score threshold. For example 3 with a block threshold of 5 challenges a lone warning rule (3) or error rule (4) and still blocks a critical rule (5).
How long a solved challenge keeps the visitor in the pass band (1 - 1440). The pass is tied to the visitor's IP address and browser.
The challenge uses the CAPTCHA provider configured on the proxy rule (the same page and provider as "Require CAPTCHA"). It is only shown to page navigations (GET requests that accept HTML). A rule without a CAPTCHA provider, and API or script clients, are blocked in the challenge band instead. Detection-only mode never challenges.
Their JSON or encoded values often look like injection attacks to the Core Rule Set and get normal visitors blocked (for example rule 942290 on PostHog's cookie). Every other cookie, argument and header is still inspected.
