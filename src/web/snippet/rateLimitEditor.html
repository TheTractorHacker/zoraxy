Rate limiting protects availability. It keeps one client from flooding a site. It is not account protection: a login still needs lockout or multi-factor sign-in in the application, and the numbers below are starting points to adjust from the 429 count in the statistics. Everything on this page is off until you set it.

Who counts as one client

By default every client IP address has its own budget. An API can count per key instead.

The header value is hashed in memory and never written to a log or a file. A request without the header is counted per IP address. To stop clients from inventing keys, each IP address also has a looser guard of 10 times the limit.

Trusted monitoring (never limited)

Requests from these addresses, or carrying the secret header, skip every rate limit of this rule.

One per line or separated by commas. The address is the real client address, so a forwarded header from an untrusted peer does not count.

Anyone who knows the header and value skips the limit, so treat it like a password and only send it over HTTPS.

WebSockets

A WebSocket starts with one HTTP request (the handshake). Today that request is counted like any other; the messages inside the open connection are never counted.

0 means no cap. Required when handshakes are not counted. Raise it when many users share one address.
