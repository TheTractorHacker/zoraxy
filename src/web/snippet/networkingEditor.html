Networking options

Client certificates (mTLS), direct peer restriction and TLS on secondary ports for this proxy rule. Every section is saved on its own and is off unless you turn it on.

Client certificates (mTLS)

  • Only visitors of this host name are asked for a certificate (selected by the TLS server name); other proxy rules are not affected. The check is repeated for the Host header, so a client cannot reach this rule through another host name's TLS session.
  • Allow / block list entries: cn:name, san:dns-or-email-or-uri-or-ip, serial:hex, a SHA-256 fingerprint (hex, colons allowed), or a bare name (matches the CN or a SAN). If an allow list exists only listed certificates pass.
  • The upstream receives X-Client-Cert-Subject, -Fingerprint, -Serial and -Verified. Headers with these names sent by the visitor are always removed first.
  • Revocation is not supported: there is no CRL or OCSP check. To cut off a certificate, put its serial or fingerprint on the block list, or replace the CA bundle.
  • HTTP (non TLS) requests to a rule that requires a certificate are refused.

Only accept connections from these peers

Only connections whose TCP peer address is in this list reach the proxy rule; everybody else gets 403 before any other check. Forwarded headers (X-Forwarded-For, CF-Connecting-IP...) are never used for this decision, so they cannot be spoofed to get in. Use it to make sure only your CDN or load balancer can talk to a rule. It applies to HTTPS, plain HTTP on port 80 and secondary ports. If Zoraxy's own listener uses PROXY protocol, the peer is the address announced in the PROXY header.

TLS on secondary listening ports

-
Without this switch the secondary listening ports speak plain HTTP. With it they use the normal certificate store (chosen by the TLS server name), the global minimum TLS version and cipher profile, and the client certificate settings above. A port is one listener: if several rules share a port and one of them asks for TLS, the port serves TLS for all of them.
