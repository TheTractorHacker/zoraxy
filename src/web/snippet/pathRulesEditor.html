How path rules work

  • Rules run in the order shown, after the access rule (blacklist / whitelist) and before WAF, CAPTCHA and login. The first matching rule decides: deny answers 403, rate limit answers 429 once the client's bucket is empty, allow stops evaluating the remaining path rules (it does not skip the WAF, CAPTCHA, login or rate limit of the proxy rule), require login forces the proxy rule's auth provider on that path even if an exception rule would skip it (and refuses the request if the rule has no auth provider).
  • Paths are normalised before they are compared. For deny, rate limit and require login a request matches if any reading of its path matches: //admin, /./admin, /x/../admin, %2e, %2f, double encoding, ;params, backslashes and NUL bytes cannot be used to slip past a rule. An allow rule only matches paths that are already clean.
  • Prefix rules match whole path segments (/admin matches /admin/x but not /administrator). Regular expressions must match the whole path. Matching is case sensitive unless you tick Ignore case; tick it if the upstream is case insensitive (IIS, Windows file systems).
  • The client address used for scopes and rate limits is the real connection address, or the address from forwarding headers only when the connection comes from a trusted proxy and the access rule trusts them.
  • Rate limits are per rule and per client address, independent of the proxy rule's global rate limit.
