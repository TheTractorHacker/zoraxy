# Admin UI audit and redesign plan (November 2026)

Goal: make the fork an advanced reverse proxy that is also easy to use, in the spirit of Cloudflare's dashboard
(task-first navigation, an expression-style rule builder, clear security overview) without giving up the single Go binary.

This is an audit of the current UI (build v3.3.6-fork.9) from screenshots of every page in light, dark and mobile
(`tools/ui-smoke`), plus the menu definition in `src/web/index.html`. It has not been checked with real users.

## 1. What the UI is today

About 30 pages in 6 menu groups, each a separate iframe component:

| Group | Pages |
|---|---|
| (top) | Quick Start, Status |
| Proxy | HTTP Proxy, Default Site, Redirection, Virtual Directories, Stream Proxy, Ingress, Advanced Rule Form |
| Security | Security Center, WAF, Access Rules, Trusted Proxies, SSO / OAuth2, CAPTCHA |
| Certificates | TLS / SSL Certificates, ACME Client |
| Observability | Statistics, Visitors, Uptime Monitor |
| Tools | Static Web Server, Network Tools, Network Interfaces, Utilities, Encrypted Client Hello, Tunnels (zrok) |
| System | Cluster / HA, Fleet, API Tokens, Update, (App Store, Plugin Manager) |

The proxy rule editor has 11 tabs (Host, Destinations, Virtual Directory, WebSocket, Alias, TLS / SSL, Headers,
Access Rules, Security, WAF, Tags). The WAF page has 9 tabs.

## 2. Findings

Ordered by how much they hurt a new or occasional user. "Evidence" names the screenshot in the smoke output.

1. **Security is spread over six pages and the per-site editor, with overlapping concepts.** Banning an address lives in
   Access Rules ("Quick Ban") and in Security Center ("Auto-ban"); admin accounts are a tab of Security Center;
   blocking by country is in Access Rules while blocking by bot or header is in Security Center; a site's own
   Access Rules, Security and WAF tabs repeat the global ones. There is no single place that answers "am I protected?".
   Evidence: `seccenter-light`, `access-light`, `waf-light`, `httprp-editor`.
2. **Safe defaults mean most protection is off.** The WAF, auto-ban and every detector start disabled
   ("Nothing changes until you turn it on"). That is a sound rule for not breaking sites, but nothing nudges a user to turn
   anything on; the WAF page has a "Start safely" box, other pages have none.
3. **The proxy rule editor is a tab per technical concept (11 tabs), not a task.** A user who wants "protect this site"
   has to visit Access Rules, Security and WAF. Evidence: `httprp-editor-waf-light`.
4. **Inconsistent save models.** The Ingress page has an "Apply" button per field; Access Rules toggles save instantly
   with a "Setting Saved" flash; the rule editor saves some fields on change and others with "Apply source" /
   "Apply challenge override" buttons; Security Center mixes plain checkboxes in a table with toggles elsewhere.
   A user cannot tell whether a change is saved. Evidence: `globalsettings-light`, `access-light`, `seccenter-light`.
5. **Unrelated settings live under the wrong names.** The interface language and default error pages are on "Ingress"
   (which was renamed from "Global Settings"); "Advanced Rule Form" sits in the Proxy group although it is a tool;
   Encrypted Client Hello and Tunnels are under Tools. Evidence: `globalsettings-light`, menu.
6. **The Certificates page opens with a raw upload form** (three file inputs) and a long tips box; what matters
   (what expires soon, which sites have no certificate) is below the fold. ACME is a separate page.
   Evidence: `cert-light`.
7. **No global search and no change history.** There is a menu filter ("/") but nothing searches sites, rules or
   settings, and a mistaken security change cannot be undone (only Fleet has versions).
8. **Jargon without help.** "Ingress", "Trusted Proxy Gating", "paranoia level", "anomaly score", "SNI",
   "Virtual Directory" appear with little or no inline explanation outside the WAF page, which is the best-explained page.
9. **Strengths to keep:** the Status page (health, traffic, blocked-today), the WAF page's "Start safely" flow and mode
   cards, the proxy table with filters and bulk actions, Quick Start for first-time users, dark mode and mobile parity,
   i18n.

## 3. Principles

1. One concept, one place. A setting is changed in exactly one page; everywhere else links to it.
2. Task first, technology second ("Protect this site", not "Access Rules / Security / WAF" tabs).
3. Safe by default and one click to recommended ("Apply recommended protection" in detection-only mode).
4. One save model across the product (see decision D2).
5. Every empty state offers the next action; every setting has a one-line plain explanation.
6. Everything is reversible: show a diff and let the user undo.
7. Light, dark and 390px mobile are checked for every page (the smoke test already does this).

## 4. Proposed information architecture

```
Overview            status, security score with fix buttons, alerts, quick start
Sites               HTTP proxy list (+ editor), default site, redirects, TCP/UDP streams
Security            overview/score, Rules (access, blocklists, geo, bots, headers, rate limits),
                    WAF, CAPTCHA & challenges, Authentication (SSO, basic auth, admin accounts),
                    Auto-ban & blocked requests
Certificates        certificates (expiring first), ACME, upload
Traffic             statistics, visitors, blocked requests, uptime
Network             listeners (today's Ingress), trusted proxies, tunnels, ECH, interfaces, network tools
Fleet & HA          Fleet, Cluster / HA
System              updates, API tokens, plugins & app store, utilities, settings (language, error pages)
```

Eight entries instead of six groups with 30 items. Existing page ids and deep links stay valid; this is mostly
navigation, grouping and cross-links first, page rewrites later.

Site editor: five sections instead of eleven tabs: **General** (host, aliases, destinations, tags), **Routing**
(virtual directories, WebSocket, headers), **Security** (access, WAF, authentication, rate limit, CAPTCHA),
**TLS**, **Advanced**; plus an Easy / Advanced switch and app presets (WordPress, Nextcloud, Home Assistant, JSON API).

## 5. Phased plan

| Phase | What | Risk | Notes |
|---|---|---|---|
| 0 | Component kit and design tokens: buttons, toggles, cards, tables, empty states, a single save bar, page template. No visible change yet | Low | Everything else builds on it |
| 1 | New menu structure, breadcrumbs, command palette (Ctrl+K) searching sites, rules, settings and pages | Low | Old tab ids and URLs keep working |
| 2 | Security overview / score page that reads existing settings and links to the fix; cross-links between overlapping pages | Low | No backend change needed beyond a read endpoint |
| 3 | Change history and undo: snapshot config on every save, show a diff, revert | Medium | Reuses the Fleet version store; needs a retention policy |
| 4 | Site editor redesign (5 sections, Easy / Advanced) and app presets | Medium | Largest UI change; one preset at a time |
| 5 | Rules page with an expression builder (Cloudflare style), unifying access, geo, bot, header, path and rate rules | High | New rule engine; Phases 0-3 first |
| 6 | Optional: AI assistant (explain an event, suggest rules into the builder, always preview and log-only first) | Medium | Off by default; own API key or local model |

Each phase ships on its own and keeps the full smoke test (every page, light/dark/mobile) green.

## 6. Decisions needed

- **D1 Framework.** Keep jQuery + Fomantic and build the component kit on it (recommended: no rewrite, ship in weeks),
  or move pages to a small modern layer (htmx/Alpine/Preact) one at a time (cleaner, slower, adds a build step to a
  currently build-free front end).
- **D2 Save model.** Explicit Save with a "unsaved changes" bar and undo (recommended for security and certificates),
  or instant save with a toast and undo.
- **D3 Defaults.** Whether new proxy rules should start with the WAF in detection-only mode and auto-ban suggested,
  instead of everything off.
- **D4 Naming.** Replace jargon in menus ("Ingress" -> "Listeners", "Virtual Directories" -> "Path routes",
  "Advanced Rule Form" -> "Raw rule form").
- **D5 Upstream drift.** These changes diverge from upstream Zoraxy's UI; merging upstream UI changes later will mean
  manual work. The fork already diverges in many places, so this is a cost to accept, not a new one.

## 7. Not decided here

The rule-builder expression language, the AI assistant's data policy, and the design of presets are separate
proposals; they depend on Phases 0-3.
