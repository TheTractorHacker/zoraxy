# Why was this blocked? (Statistics > Blocked)

From a visitor's 403 (or an admin's hunch) to the rule that fired and a previewed, undoable fix, without a new menu item or page.

* **Reference ID.** Block pages show `ZX-XXXX-XXXX` and send `X-Zoraxy-Ref`. The Blocked tab search box, the Ctrl+K palette and the Status "Blocked today" tile ("See why") all lead to it. A typed Reference ID (`ZX-` + 8 characters) or a full IP address is looked up with `GET /api/blocked/lookup`; anything else filters host, path and rule as before. A found ID shows as a removable tag and opens the drawer; a missing one shows the "No block with this ID" state (the log keeps the last N entries; logging may be off) with a link to the log settings.
* **Table.** User-Agent column (hidden under 900px, full text in the tooltip and the drawer), the Reference ID under the time, the reason chip plus the category as a link to the rule, and a "Why" chevron button on every row (keyboard path to the drawer). The Top IPs card is hidden while it would list one address.
* **Drawer** (`ZxUI.drawer`). Sentence from `/api/blocked/explain` (English text from the server), the fix choices as radios with risk and scope badges, the live preview line and the before/after list, then the details. Apply stays disabled until a choice is made; a fix that changes all sites needs an extra checkbox and is never preselected. Apply sends the `previewId` of the shown preview; a stale preview is refused and reloaded. Success closes the drawer and shows an Undo toast for 15 seconds (with a History link); the change is recorded in History. "Open rule" jumps to the page that owns the rule.
* **Bot rules page.** One read-only line when a rule's action is Challenge and no site has a working CAPTCHA (`CaptchaSites` of `GET /api/botrules/get`).
* **Allow this User-Agent on this site (`bot-ua-allow`).** For a bot block the narrowest fix is offered first (and preselected): requests whose User-Agent contains a pattern skip the bot rules on that site only. The pattern is stored as `BotAllowUA` (lower-case substrings, `omitempty`, at most 20 entries of 4 to 64 characters) on the site's proxy rule and written through `applyNetworkingChange`, like the other networking settings, so History and the config file show it. The drawer prefills the product token only (`curl/` for `curl/8.18.0`) in an editable field; each edit asks `GET /api/blocked/explain?...&pattern=` for the exact preview (the `previewId` covers the pattern). Refused: Mozilla-style User-Agents (no fix is offered and a note says why), patterns that are short, generic (`mozilla`, `chrome`, `bot`, `http`, ...) or part of what ordinary browsers send, and patterns that are not part of this client's User-Agent. Not offered for a failed fake-bot check, an empty User-Agent, or a site whose bot rules are already off. The preview says exactly what changes ("requests whose User-Agent contains "curl/" skip the bot rules on <site> only. Other sites unchanged.") and warns that a User-Agent is trivially spoofable. In the hook (`mod/dynamicproxy/bot_hook.go`) the list is checked before `Evaluate`, case-insensitively, and only when every User-Agent header value matches (a second header cannot smuggle a bot past it). Undo removes only that entry and refuses if it is gone. The site editor (Security, card "Exploit and crawler blocking") lists the entries with a remove button each (`POST /api/botrules/allowua`, `op=remove|add`); the list is hidden while empty, so Easy mode is unchanged, and a non-empty list makes the card show in Easy mode like any non-default setting.
* **Not done.** Per-site "turn bot rules off" remains the blunt alternative; localised sentences (the explanation text is English), request simulator, hit counters.
